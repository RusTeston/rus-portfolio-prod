Component Mapping — On-Premises to AWS
On-Premises AWS Equivalent Why This Service
Cisco ASA Firewall (HA) → AWS WAF + Network Firewall Managed firewall rules with automatic failover. No hardware to maintain, scales with traffic.
F5 LTM Load Balancer → Application Load Balancer (ALB) Layer 7 load balancing with path-based routing, health checks, and SSL termination built in.
2x Web Servers (DMZ, VLAN 100) → CloudFront + S3 (Static Assets) Static content served globally from the edge. Dynamic requests forwarded to the app tier via ALB.
4x App Servers (VLAN 200) → EC2 Auto Scaling (Private Subnets, 2 AZs) Auto Scaling replaces manual capacity planning. Multi-AZ deployment eliminates single points of failure.
SQL Server Cluster (VLAN 300) → RDS SQL Server Multi-AZ Managed database with automated backups, patching, and synchronous standby replication across AZs.
NetApp AFF SAN (Fibre Channel) → Amazon EBS (gp3) + S3 EBS for block storage attached to EC2. S3 for object/file storage with 11 nines durability.
Cisco Catalyst Core Switch → VPC + Subnets + Route Tables Software-defined networking replaces physical switching. VLANs become subnets with security groups as firewalls.
MPLS WAN to Chicago DR Site → Multi-AZ + AWS Backup + S3 Cross-Region Multi-AZ provides built-in DR within the region. AWS Backup and S3 Cross-Region Replication replace the Chicago MPLS link entirely.
Manual Monitoring / Syslog → CloudWatch + CloudTrail + VPC Flow Logs Unified observability, audit logging, and network traffic visibility — all managed, no servers required.
Key Business Benefits
💰
Cost Optimization
Eliminate hardware refresh cycles, data center costs, and the Chicago MPLS circuit. Pay only for compute actually consumed. Estimated 30–45% reduction in infrastructure spend.
⚡
Scalability & Resilience
Auto Scaling handles traffic spikes automatically. Multi-AZ deployment provides 99.99% availability without a separate DR site or manual failover procedures.
🔧
Operational Efficiency
AWS manages patching, hardware failures, and database backups. Engineering teams focus on application features instead of infrastructure maintenance.
Recommended Migration Approach
1
Foundation — VPC, Networking & Security (Weeks 1–3)
Build the VPC with public/private subnets across 2 AZs, configure Security Groups, WAF, ALB, Route 53, and ACM certificates. Establish Direct Connect or VPN for hybrid connectivity during migration.
2
Database Migration — RDS SQL Server (Weeks 4–6)
Use AWS Database Migration Service (DMS) to migrate SQL Server to RDS Multi-AZ with minimal downtime. Validate data integrity and application connectivity before cutover.
3
Application Tier Migration — EC2 + Auto Scaling (Weeks 7–9)
Rehost application servers to EC2 using AWS Application Migration Service. Configure Auto Scaling groups, launch templates, and load balancer target groups. Run parallel environments for validation.
4
Cutover, Optimization & DR Decommission (Weeks 10–12)
DNS cutover via Route 53, decommission Chicago DR site and MPLS circuit, enable CloudWatch dashboards, AWS Backup policies, and S3 Cross-Region Replication. Decommission on-premises hardware.
